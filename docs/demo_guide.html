1Simulation set-up

The chair's Crazyflie digital twin runs in Docker: Ubuntu 22.04, ROS 2 Humble, Webots R2025a, eight Crazyflie drones (cf231–cf238). Each drone has its own HTTP control service on ports 5000–5007.

What we useHow
StatusGET /status → state, phase, position, battery, sim_time
Commands/activate_idle, /begin_takeoff, /navigate, /begin_landing
Finished?GET /tasks/<id> (HTTP 200 only means "accepted")

Rules we learned

  • Landing: after landing, state stays "landing"; phase becomes "landed". Our scripts wait for the phase.
  • Time: the simulation can be slower than real time, so all waiting uses sim_time, and each script checks that the clock moves.
  • Battery: the simulator reports a fixed dummy value, so battery levels for planning come from our world model (world.json).

2Mission language (Mission JSON)

Our own small language for missions, defined by a JSON Schema (pipeline/mission_schema.json). It is the contract between the LLM, the validators and the compiler.

The rules

ActionRequired fieldMeaning
takeoff– (optional altitude_m ≤ 1.5)climb to cruise height
gototarget = a place name, never coordinatesfly to a named place
pickupparceltake a parcel at the current place
dropoffparceldeliver it at the current place
holdduration_s (0–120)hover for some seconds
land–land
  • Task ids are t1, t2, …; the tasks of one drone run in list order.
  • "after": ["t5"] makes a task wait for a task of another drone ("then" in the request).
  • An impossible request = "tasks": [] plus a reasoning (refusal).
  • No other fields are allowed (additionalProperties: false).

4Validators and correction loop

validators.py checks every mission in two layers and explains each error in one sentence. It is normal Python code, not a second LLM, so the same mission always gets the same answer.

RuleChecks
S1/S2form of the mission and of each task (JSON Schema)
S3task ids unique; after points to existing tasks
A1drone exists
A2drone idle and battery ≥ 30 %
L1place and parcel exist
P1parcel mass ≤ payload limit
Q1each drone starts with takeoff and ends with land
Q2pickup at the parcel's place; drop off only what is carried
Q3one parcel at a time; each parcel picked up by one drone
Q4no circular waiting through after

Example: a mission that uses the drone with 22 % battery

This exact text goes back to the LLM in the correction loop.

LLM→mission→validators→valid: execute
errors→back to LLM (max. n rounds)→still invalid: refuse, nothing is flown

Lesson: wording of the feedback matters

When the feedback listed all valid places, the model replaced the unknown "warehouse" with "depot_a" instead of refusing. Rule L1 (v2) now suggests a fix only for a likely typo and otherwise says: "Do not replace it with another place."

5Mission compiler with 4D paths (in progress)

Phase A works: fly_mission.py separates drones by altitude layer. Phase B replaces layers with collision-free paths in space and time from 4DPlanning (Sow et al., AAMAS 2026).

How 4DPlanning works

  • Input: a voxel map (small cubes, obstacles, timed no-fly zones) and one line per drone: start, goal, start time, radius, speed.
  • Output: one cube per time step for each drone; the same cube again means waiting.
  • Method: plan drones by priority, then repair remaining conflicts.

Our plan

  1. Map the hall to cubes (proposal: 0.1 m cubes, 0.5 s steps).
  2. Turn each goto leg into a planner agent with a start time.
  3. Run the planner, convert cubes back to metres and seconds.
  4. Keep only corner points and waits; check distances independently.
  5. Fly with a common start time and timed navigate commands.

Question for the TA: 4DPlanning plans one start and one goal per drone and keeps the drone at its goal. A delivery has several legs (start → depot → destination). How should we map legs onto planner agents? Which cube size and time step are realistic?

6–7Speech input and evaluation (planned)

  • Task 6: Whisper (faster-whisper, small model) on the CPU, because the GPU is busy with Qwen. Push-to-talk; known names (places, parcels, drones) given as a hint. First test with recorded WAV files.
  • Measure speech: word error rate and entity accuracy (every drone, place and parcel name heard correctly).
  • Task 7: run every test command typed and spoken, with and without validators, with 2 to 8 drones. Metrics: correct missions, drone choice vs. a simple rule, success rate, response time per stage.
  • Known limit: validators catch invalid missions, not valid-but-wrong ones (e.g. "depot B" heard instead of "depot A").
